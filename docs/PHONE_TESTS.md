# Проверка N70Test 0.9.1 на телефоне

Установить `dist/N70Test.sis` поверх предыдущей версии, закрыв старое приложение.
На главном экране должна быть версия **0.9.1**. Нужны правильные дата и время,
доступ в Интернет через Internet-точку доступа и примерно 200 КиБ свободного
места на C: для файла и журналов. Настройка случайности вручную не требуется.

0.9.1 исправляет зависание 0.9.0 на повторе GET 503, TCP timeout и выходе из
приложения при активном запросе. Сначала повторить **Test client 0.9**, затем
**Test TCP timeout**. Имена меню сохранены; начало новых журналов — N70Test 0.9.1.
Исправление подтверждено новыми журналами: client 14/14, TCP 2/2 (2140/2031 мс).
[Результаты 0.9.1 на N70](N70_RESULTS_0.9.1.md). Неполные журналы также полезны:
START сохраняется перед каждым тестом. [Причина сбоя](N70_RESULTS_0.9.0.md).

## Новое: Options → Test client 0.9

Ожидаемый итог **14/14 checks passed**, журнал
`C:\system\apps\N70Test\client-tests.txt`. Запуск может занять несколько минут:
некоторые проверки намеренно открывают новые TLS-соединения и ждут повтора.
При переподключении возможен повторный выбор точки доступа.

1. PUT с JSON: метод и разобранные данные возвращаются сервером.
2. PATCH с JSON: тот же контроль метода и тела.
3. DELETE с JSON: тот же контроль метода и тела.
4. Второй GET после прогрева использует TLS: Reused=1, NewTCP=0, Retries=0.
5. Отключение keep-alive даёт новое соединение: NewTCP=1, Reused=0.
6. После DisconnectL следующий GET снова подключается: NewTCP=1.
7. GET `/status/503`: три попытки, два повтора, окончательный 503 выдан sink один раз.
8. При выключенных повторах GET `/status/503` выполняется один раз.
9. POST `/status/503` выполняется один раз даже с iRetryIdempotent=ETrue.
10. PATCH `/status/503` также не повторяется.
11. PUT `/status/503` не повторяется с настройками по умолчанию.
12. PUT `/status/503` с явным opt-in и бюджетом 1 выполняется два раза.
13. Заголовок Retry-After: 1 распознан как RetryAfterMs=1000; HTTP 200 не повторяется.
14. После простоя 800 мс при лимите reuse 500 мс открывается новое соединение.

Attempts/Retry/NewTCP/Reused/AddressAttempts добавлены в журналы. Здесь HTTP 503
ожидаем: это проверка политики повторов, не ошибка TLS. Сервер httpbingo.org
не даёт комбинировать заданный статус и Retry-After в одном таком ответе:
совместные правила задержки, HTTP-date и пределов проверяются на ПК.

DisconnectL проверяет освобождение и новый запуск собственных handles.
Реальное отключение радио, смену сети и недоступность первого DNS-адреса
надо проверить отдельно на N70; на ПК соответствующие сценарии моделируются.
В тестах нет автоматических повторов запросов к реальным учётным записям.

## Новое: Options → Test API + gzip

Ожидаемый итог — **12/12 checks passed**. Журнал:
`C:\system\apps\N70Test\api-tests.txt`.

1. `/bearer` без токена возвращает HTTP 401 без ошибки TLS.
2. `SetBearerTokenL` отправляет публичный тестовый токен; `/bearer` его подтверждает.
3. `SetHeaderL` заменяет X-N70-Test без учёта регистра; сервер видит новое
   значение и переопределённый Accept, старого значения нет.
4. Редирект внутри httpbingo.org сохраняет Bearer и проходит авторизацию.
5. `/gzip` возвращает распакованный JSON; WireBytes меньше Bytes.
6. `/stream/20` одновременно использует gzip и chunked: после декодирования 20 строк.
7. Лимит распакованного тела 32 байта даёт -9, в sink не уходит лишнее.
8. Сервер объявляет Content-Encoding gzip, но отправляет обычный JSON:
   ожидается KErrCorrupt (-20), а не выдача неверного тела.
9. Загрузка `/gzip` сохраняет распакованный `gzip-response.json` с верным размером.
10. CRLF в пользовательском заголовке отклоняется с -6 до сети.
11. Переопределение Host отклоняется с -6 до сети.
12. Некорректный Bearer-токен отклоняется с -6 до сети.

В журнале Gzip/Chunked относятся к исходным HTTP-заголовкам; Bytes — к
распакованному телу, WireBytes — к телу до распаковки. Последние три проверки
локальные: TLS/Stage в их диагностике могут оставаться от предыдущего запроса.
Токен `n70-public-test-080` — фиктивный, реальную учётную запись не использует.
Автоматическое удаление заголовков при смене origin дополнительно проверяется
на ПК; данный сетевой набор проверяет сохранение при переходе внутри origin.

## Новое: Options → Test TCP timeout

Журнал — `tcp-timeout.txt` в той же папке. После прогрева bearer запускаются
два запроса на зарезервированные TEST-NET адреса:

- 192.0.2.1: I/O timeout 2 с, общий предел 5 с;
- 198.51.100.1: общий предел 2 с, I/O timeout 10 с.

Ожидается -33 на стадии tcp-connect примерно за 2 секунды; PASS допускает
1800–3500 мс, включая накладные расходы. Измерение Wall elapsed ведётся по UTC
для диагностики, также записывается разница TickCount; часы телефона во время
проверки не менять. Сама библиотека использует RTimer, календарное время её
таймаутами не управляет. Ожидание около 153 с должно дать FAIL.

Оператор может немедленно отклонить подключение к TEST-NET или перехватить его.
В этом случае будет **INCONCLUSIVE**, с фактической ошибкой и стадией: нужного
зависания не произошло, такой результат не считается успешной проверкой таймаута.
Отправлять к этим адресам HTTP-данные или секреты не требуется.

Эти функции повторно проверены версией 0.9.1 на N70. Текущие журналы
`tests/device/n70-0.9.1` подтверждают 12/12 API/gzip и 13/13 основных HTTP-проверок.

## Один запуск: Options → Test new features

Все запросы идут на `https://httpbingo.org/`. Описание сервиса и его ресурсов:
[go-httpbin](https://httpbingo.org/). Это внешний сервис; доступность и цепочка
сертификатов могут меняться. Обычные сетевые тесты требуют проверенного TLS 1.2,
а проверки таймаута и отмены могут прерваться ещё до завершения рукопожатия.

| № | Проверка | Условие PASS |
|---|---|---|
| 1 | GET `/get` | HTTP 200, однократный вызов заголовков, непустое тело |
| 2 | HEAD `/get` | HTTP 200, Content-Type, ноль байтов тела |
| 3 | POST JSON `/anything` | Сервер сообщает метод POST и возвращает разобранное поле `n70=tls12-json-071` |
| 4 | POST формы `/anything` | Сервер сообщает POST, возвращает отправленные данные и тип формы |
| 5 | GET `/redirect/1` | Один переход, финальный URL `/get`, HTTP 200 |
| 6 | POST → 303 → `/anything` | Один переход; сервер получил GET с пустым телом, исходный маркер отсутствует |
| 7 | POST → 307 → `/anything` | Один переход; POST и разобранные JSON-данные сохранились |
| 8 | Chunked `/stream/20` | Тело декодировано из chunked, содержит ровно 20 строк |
| 9 | HTTP 404 | Метод вернул статус 404 без Symbian-ошибки |
| 10 | Лимит тела 128 байтов, ответ `/bytes/4096` | `KErrOverflow` (-9), передано не больше разрешённого числа байтов |
| 11 | Загрузка `/bytes/131072` | `download.bin` содержит ровно 131072 байта; размер результата совпадает |
| 12 | Неудачная замена файла | Повторная загрузка нарушает лимит; SHA-256 и размер прежнего файла не изменились |
| 13 | `/delay/10` с общим сроком 2 секунды | `KErrTimedOut` (-33) |

Тест 11 перезаписывает только собственный тестовый файл
`C:\system\apps\N70Test\download.bin`. Вся страница/загрузка не хранится в памяти:
потоковый обработчик считает байты и сохраняет до 2048 байтов начала ответа,
а загрузчик пишет файл порциями. Два вычисления SHA-256 также читают файл порциями.

Результаты — `C:\system\apps\N70Test\http-features.txt`. Для каждого пункта
записываются START, адрес, PASS/FAIL, фактическая и ожидаемая Symbian-ошибка,
HTTP-статус, число байтов, переходов, версия TLS, ошибки BearSSL/I/O, стадия,
финальный URL и начало текстового ответа. После тестов приложение показывает
`13/13 checks passed`; журнал заканчивается `Summary: 13/13 passed. Cancelled=0`.
Обнаруженные сетевые ошибки не останавливают остальные пункты; отмена останавливает.
Ошибка открытия журнала, выделения памяти или другая ошибка подготовки может
завершить серию раньше; приложение покажет стадию сбоя.

У теста лимита HTTP может быть 0: при известном слишком большом Content-Length
библиотека отклоняет ответ до выдачи заголовков вызывающему приложению.
Ожидаемые -9 и -33 означают PASS именно в соответствующих отрицательных тестах.
Серия из 13 проверок сама не требует нажимать Cancel request.

## Отдельно: Test timeout

Результат — `timeout.txt` в той же папке. Сначала HEAD-запрос устанавливает
соединение с выбранной точкой доступа вне двухсекундного отсчёта. Затем
запускается `/delay/10` с общим сроком 2 секунды. Ожидается `-33` и `1/1 passed`.
В срок входит TCP/TLS-рукопожатие, если reuse не состоялся; N70 может прервать его до
начала ожидания ответа сервера. Это проверка общего срока, а не скорости TLS.

## Отдельно: Test cancellation

1. Выбрать **Options → Test cancellation**.
2. После выбора точки доступа во время запроса открыть **Options → Cancel request**.
   Сервер задерживает ответ на 10 секунд; нажать отмену до завершения запроса.
3. Проверить `cancel.txt`: ожидается `Error=-3 expected=-3`, PASS и `1/1 passed`.
4. Повторно запустить **Test HTTPS** или **Test new features**: новый запрос
   должен работать, так как токен отмены сбрасывается между запусками.

Если отменить ещё прогревочный HEAD-запрос, журнал покажет отмену прогрева,
а специальная проверка ожидания не будет засчитана. Если не нажать отмену,
успешный HTTP-ответ означает FAIL этого теста: требовалось прервать запрос.
Отдельный Test cancellation проверяет отмену сетевого запроса; проверка
файла в основной серии проверяет ошибку лимита, а не ручную отмену загрузки.

## Что ещё проверять отдельно

Новые тесты нужно запускать на настоящем N70: успешная сборка и хостовые
проверки на Windows не подтверждают работу Symbian-сокетов на устройстве.
Отключение сети, нехватка диска, выключение питания при записи и отмена посреди
файловой загрузки не имитируются автоматически этим набором.
